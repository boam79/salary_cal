## 프로젝트 개요
10가지 금융 계산기와 종합뉴스를 제공하는 SPA 웹앱

## 주요 기능

### 계산기 (10종)
1. 월급/연봉 - 2025년 세율 기준
2. 세금 - 상속세, 증여세
3. 부가세 - 공급가액↔총액, 환급
4. 부동산 - 중개수수료, 양도세, 보유세, DSR
5. 취등록세 - 부동산 취득/등록세
6. 대출 - 원리금균등/원금균등/만기일시
7. 적금/예금 - 단리/복리, 이자세
8. 퇴직금 - 입퇴사일 기반
9. 자동차 취득세 - 차종별 세율
10. 로또번호 - 빈도 기반 생성

## 분석 및 제안 (Planner)

### 관찰된 핵심 리스크
- **즉시 크래시 가능성**: `js/main.js`에서 `topNewsManager`를 제거했다고 주석 처리했지만, `cleanup()`에서 `topNewsManager.cleanup()`을 호출하고 있어 런타임 에러 가능성이 큽니다. (현재 `topNewsManager` import도 없음)
- **설정의 단일 출처(SSOT) 불일치**: 세율은 `config/rates.json`로 중앙화돼 있으나, 최저시급은 `AppState`에도 있고 `salary.js`에는 `10030`이 하드코딩돼 있습니다. 이 상태면 업데이트 시 누락/불일치가 생깁니다.
- **자동화 테스트 부재**: 테스트 파일이 없어서(현재 기준 0개) “세율 업데이트/공제구간 변경/수식 수정” 같은 변경이 들어올 때 회귀를 막기 어렵습니다.
- **프론트-백엔드 계약(Contract) 고정 부족**: `/lotto/*` API는 기능이 많고 폴백도 포함돼 있는데, 응답 스키마/에러코드/캐시 정책이 테스트/문서로 고정돼 있지 않습니다.
- **디버그 로그 과다**: 뉴스 렌더링에서 카드 생성마다 `console.log`가 많아 성능/개인정보(일부 필드)/운영 로그 노이즈 리스크가 있습니다.

### 우선순위 제안
1. **P0 (즉시)**: `topNewsManager` 관련 cleanup 크래시 가능성 제거(또는 import 복구) + 빠른 스모크 확인.
2. **P1 (정확성/회귀 방지)**: 계산기 핵심 수식(연봉/세금/대출/퇴직금/부가세)의 “대표 케이스”를 자동 테스트로 고정.
3. **P1 (설정 일원화)**: 최저시급/보험요율/공제구간 등 “연도별로 변하는 값”을 `config/rates.json` 또는 별도 `config/constants.json`로 통합하고, 코드에서 하드코딩 제거.
4. **P2 (운영 품질)**: 뉴스/통계/로또 API의 에러 처리/로그 레벨/캐시 정책을 문서화 + 최소 모니터링(health/uptime) 점검.
5. **P3 (SEO/UX)**: SPA 특성상 계산기별 딥링크/메타 태그/OG가 제한될 수 있어, sitemap/라우팅 전략을 재검토(필요 시).

- [ ] **연봉/월급 계산기 핵심 케이스 테스트**  
  - 성공 기준: (연봉 모드) 특정 연봉 입력 시 세율/공제/4대보험 계산 결과가 스냅샷/근사치 검증으로 통과. (월급 모드) 최저시급 경계값(=최저시급, <최저시급) 동작이 테스트로 고정.
- [ ] **세금(상속/증여) 구간 테스트**  
  - 성공 기준: 각 누진구간 경계값(최대값 바로 아래/같음/초과) 3점씩 검증.
- [ ] **대출(상환방식 3종) 테스트**  
  - 성공 기준: 원리금균등/원금균등/만기일시에서 총이자·월납입 로직이 대표 입력 2~3세트로 검증.
- [ ] **부가세/적금·예금/퇴직금/취등록세/자동차 취득세 스모크 테스트**  
  - 성공 기준: 각 계산기별 최소 1개 입력 세트가 “NaN/음수/빈값/표시 누락 없이” 정상 렌더 가능한 계산 결과를 산출.
- [ ] **로또 백엔드 API contract 테스트(서버)**  
  - 성공 기준: `/health`, `/lotto/stats`, `/lotto/generate`가 정해진 JSON 스키마를 만족(필수 필드 존재, 타입 일치).

### 6. 문서화
